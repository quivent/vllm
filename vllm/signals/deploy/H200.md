# H200: provisioning, exactly

The machine this was verified on. Follow top to bottom on a fresh Hopper x86
box and you get a serving Qwen3.8-27B with residual capture at full speed.

**Target profile**

| | |
|---|---|
| GPU | NVIDIA H200 NVL, 143,771 MiB |
| host | x86_64, Ubuntu 22.04.5, 16 cores |
| driver | **580.126.09** — CUDA 13 native, *no compat shim needed* |
| model | `RedHatAI/Qwen3.8-27B-INT4` (hidden 5120, 64 layers, MTP) |

---

## 0. One command

```bash
git clone https://github.com/quivent/vllm ~/vllm
cd ~/vllm && git checkout signal-extraction-capture
VLLM_SERVER_DEV_MODE=1 ./vllm/signals/deploy/preflight.sh --fix
```

Fix whatever it still reports, then follow the steps it points at. The rest of
this file is what that script encodes, in case you need to do it by hand.

---

## 1. System packages

```bash
sudo apt-get update && sudo apt-get install -y g++
```

`g++` is not optional. flashinfer JIT-compiles its sampler through `nvcc`, which
shells out to the host compiler; a box with `gcc` but no `g++` fails minutes into
startup with `cannot execute 'cc1plus'` → `nvcc fatal`. This box had gcc, nvcc
*and* ninja and still died on it.

## 2. Python environment

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"          # uv and gemstone live here;
                                              # a non-login shell omits it
cd ~/vllm && uv venv --python 3.12
export PATH="$HOME/vllm/.venv/bin:$PATH"

VLLM_USE_PRECOMPILED=1 VLLM_PRECOMPILED_WHEEL_VARIANT=cu130 uv pip install -e .
uv pip install ninja                          # flashinfer's JIT needs it
```

**Pin `cu130`.** Auto-detection probes for a `cu129` variant that is not
published for this commit, and the build dies with
`Failed to fetch precompiled wheel metadata`. This vLLM is a CUDA 13.0 build
(`VLLM_MAIN_CUDA_VERSION=13.0`, `torch==2.13.0+cu130`).

Verify before going further:

```bash
python -c "import torch; assert torch.cuda.is_available(); print(torch.__version__)"
# 2.13.0+cu130
```

If that fails on a driver **older than r580**, install the arch-correct
forward-compat package (`x86_64` here, `sbsa` on Grace) and put it on
`LD_LIBRARY_PATH` — see `README.md`. On driver 580 you do not need it.

## 3. CUDA toolkit for the JIT

No system toolkit is required; the venv's pip CUDA package provides `nvcc`:

```bash
export CUDA_HOME="$HOME/vllm/.venv/lib/python3.12/site-packages/nvidia/cu13"
export PATH="$CUDA_HOME/bin:$PATH"
```

**If flashinfer still fails after this and after `g++`:** clear its poisoned
build cache (`rm -rf ~/.cache/flashinfer`), and if it persists, set
`VLLM_USE_FLASHINFER_SAMPLER=0`. That is what this box needed. The sampler is
not what capture touches, so bypassing it costs nothing here.

## 4. Model

```bash
hf download RedHatAI/Qwen3.8-27B-INT4 --local-dir ~/models/RedHatAI/Qwen3.8-27B-INT4
```

**Do not pull the R2 `models/` prefix.** It is content-addressed
(`blobs/refs/trees`) and yields 19 GB with no `config.json`. Either use the HF
pull above (~1 minute on this link) or `gemstone models download --local-dir`.

## 5. Clear the GPU

```bash
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv
sudo docker ps                       # a restart policy will respawn a container
sudo docker stop <id>
sudo systemctl stop gemstone-governor-agentic-8000.service
```

This box shipped with a Gemma-4-31B governor stack holding 74 GB, supervised by
both Docker and systemd — stopping the process alone is not enough, it comes
back. To restore it later:

```bash
sudo docker start vllm-gemma4-fp8-h200
sudo systemctl start gemstone-governor-agentic-8000.service
```

## 6. Serve

`~/start-qwen-graph.sh` on the box; equivalently:

```bash
export VLLM_SERVER_DEV_MODE=1                 # or /signals/* will 404
export VLLM_CACHE_ROOT="$HOME/.cache/vllm-signals"
export CUDA_HOME="$HOME/vllm/.venv/lib/python3.12/site-packages/nvidia/cu13"
export PATH="$CUDA_HOME/bin:$HOME/vllm/.venv/bin:$PATH"
export VLLM_USE_FLASHINFER_SAMPLER=0

vllm serve \
  --model "$HOME/models/RedHatAI/Qwen3.8-27B-INT4" \
  --served-model-name qwen38 --port 8001 --host 0.0.0.0 \
  --kv-cache-dtype fp8 --attention-backend TRITON_ATTN \
  --max-model-len 131072 --max-num-seqs 512 --gpu-memory-utilization 0.85 \
  --enable-prefix-caching \
  --speculative-config '{"method": "mtp", "num_speculative_tokens": 3}' \
  --trust-remote-code \
  --signal-capture-backend graph \
  --signal-capture-max-tier residual_raw \
  --signal-capture-tier residual_raw \
  --signal-capture-layers last --signal-capture-tokens last \
  --signal-capture-dir "$HOME/signals"
```

Startup is ~4 minutes: weights, torch.compile, then 83 PIECEWISE + 2 FULL CUDA
graphs at ~1.3 graphs/s. (On the Grace box the same capture runs at 12.3 *seconds
per graph* — ~17 minutes. It is host-bound single-thread work, not a hang.)

## 7. Verify

```bash
python -m vllm.signals.bench --port 8001 --dir ~/signals
```

Expect 11 ok, 1 warn, 0 fail. The warn is the bench's own spec detector giving a
false negative — confirm speculation directly:

```bash
curl -s localhost:8001/server_info | grep -o "SpeculativeConfig([^)]*"
# SpeculativeConfig(method='mtp', num_spec_tokens=3, ...)
grep -c "Cudagraph is disabled under eager mode" <serverlog>    # must be 0
```

`0` there is the whole point: capture is running with CUDA graphs on.

## 8. Ship the captures

```bash
python -m vllm.signals.r2 --dir ~/signals --backend gemstone watch &
```

Objects land under `signals/<model>/<session>/<day>/`, catalogued in
`signals/_catalog/<day>.jsonl`. Give each machine its own
`--signal-capture-session` so the corpus stays separable.
